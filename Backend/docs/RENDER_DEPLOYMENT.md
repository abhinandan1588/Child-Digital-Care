# Deploying to Render

This repository keeps the backend in `Backend/` and the Render Blueprint at the
repository root (`render.yaml`), because Render only looks for a Blueprint
there.

> **Before the first deploy, read [Rotating leaked
> credentials](#rotating-leaked-credentials).** The database password and the
> JWT signing key that were committed to this repository are public and must be
> replaced. Deploying with them would publish an openly accessible service.

---

## What the platform gives you and what the app needs

| App requirement | Render provides | Handled by |
| --- | --- | --- |
| Listen on an assigned port | `PORT` env var | `dockerCommand` passes `--port $PORT`; the Dockerfile falls back to 8000 |
| Run behind a TLS terminator | HTTPS proxy | `--proxy-headers --forwarded-allow-ips '*'` |
| asyncpg driver URL | libpq `postgres://` URL | `normalize_database_url` in `app/core/config.py` |
| Schema migrated before serving | pre-deploy command (paid) or start command | `alembic upgrade head` in `dockerCommand` |
| Secrets outside the repo | env vars, `generateValue`, `sync: false` | `render.yaml` |
| RS256 keys without a file mount | env vars only | `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` inline PEM |

Two of those needed code changes, both now in place:

**The connection string.** Render hands out a libpq URL
(`postgresql://user:pass@dpg-xxxx-a/db`, and `?sslmode=require` on the external
one). Neither part works unchanged. Without a driver in the scheme SQLAlchemy
loads synchronous psycopg, which this project does not install, so the engine
dies with `ModuleNotFoundError: No module named 'psycopg2'`. And SQLAlchemy's
asyncpg dialect forwards every query parameter straight into
`asyncpg.connect()`, which has no `sslmode` argument — it spells that setting
`ssl` — so the connection dies with `TypeError: connect() got an unexpected
keyword argument 'sslmode'`. `normalize_database_url` rewrites both, so the
value can be pasted from the dashboard unedited.

**The RS256 keypair.** Production requires RS256, and the only way to give
Render a secret is an environment variable. `JWT_PRIVATE_KEY` and
`JWT_PUBLIC_KEY` now accept inline PEM text alongside the existing
`*_PATH` variables. Web consoles often turn the newlines in a PEM block into
the two characters `\n`; that is detected and repaired, because otherwise PyJWT
reports a malformed key and it reads like a wrong-key problem.

## Deploy with the Blueprint

1. **Rotate the leaked credentials first** (see below).

2. Commit and push the deployment files:

   ```bash
   git add .gitignore render.yaml Backend/
   git commit -m "Add Render blueprint; move secrets out of the repo"
   git push
   ```

3. In the Render dashboard: **New → Blueprint**, pick this repository, and let
   it read `render.yaml`.

4. Render prompts for the two `sync: false` values. Paste the **internal**
   connection strings from your existing instances:

   | Variable | Where to find it |
   | --- | --- |
   | `DATABASE_URL` | Postgres instance → Connect → **Internal Database URL** |
   | `REDIS_URL` | Key Value instance → Connect → **Internal Key Value URL** |

   Internal URLs work only between services in the same region, which is why
   `render.yaml` pins `region: singapore` — match it to your instances. Nothing
   else needs editing for the first deploy; `SECRET_KEY` is generated by Render.

5. Watch the deploy log. A healthy first boot shows the migration running, then
   the app reporting its environment:

   ```
   INFO  [alembic.runtime.migration] Running upgrade  -> d59a190f423e, initial schema
   {"event": "application_starting", "env": "staging", "docs_enabled": true, ...}
   ```

6. Verify the running service:

   ```bash
   BASE=https://child-digital-care-api.onrender.com
   curl -s $BASE/health/live
   curl -s $BASE/health/ready     # {"database":"ok","redis":"ok"}
   curl -s -o /dev/null -w '%{http_code}\n' $BASE/openapi.json
   ```

   Swagger UI is at `$BASE/docs`. It is served because `APP_ENV=staging`;
   production disables it (see the promotion checklist).

7. Create the first admin and seed the permission catalogue, from the service's
   **Shell** tab:

   ```bash
   python -m app.scripts.seed_admin_rbac
   python -m app.scripts.create_admin
   ```

### Without a Blueprint

The same thing through the dashboard: **New → Web Service**, select this repo,
then set Language `Docker`, Dockerfile Path `./Backend/Dockerfile`, Docker
Build Context Directory `./Backend`, Health Check Path `/health/live`, and the
Docker Command from `render.yaml`. Add every `envVars` entry by hand, and
generate `SECRET_KEY` yourself:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

### Native Python runtime instead of Docker

Docker is the recommended path: the image pins Python 3.12, installs only the
runtime dependencies, and runs as a non-root user. If you prefer Render's
native Python runtime:

- Root Directory: `Backend`
- Build Command: `pip install .`
- Start Command:
  `alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips '*'`

Use `pip install .`, **not** `pip install -r requirements.lock`. That lock file
is a full freeze of the development virtualenv: it pulls in pytest, mypy, ruff,
`firebase-admin` and `grpcio`, which lengthens every build and ships test
tooling to production. `pip install .` installs exactly the pinned runtime
dependencies from `pyproject.toml`.

Render's native runtime currently defaults to a newer Python than the
Dockerfile's 3.12. The project supports `>=3.12` and its test suite passes on
3.14, but pin `PYTHON_VERSION` explicitly so a platform default change cannot
alter your runtime underneath you.

## Free plan limitations that affect this app

These are platform behaviours, not bugs to fix:

- **Idle spin-down.** A free web service sleeps after 15 minutes without
  traffic. The next request pays a cold start, and every open WebSocket is
  dropped — so realtime command delivery stops while the service is asleep.
  Child devices fall back to polling `/device/sync`, which is the designed
  behaviour, but push-style delivery needs an always-on instance.
- **No background worker.** Background workers require a paid instance type, so
  the Celery entry in `render.yaml` is commented out. Without it nothing on the
  beat schedule runs: outbox publishing (so no FCM wake-ups), command and
  pairing-invitation expiry, stale-device marking, retention sweeps, and due
  account deletions. The API works; this maintenance does not happen.
  **Retention sweeps and due deletions not running is a privacy commitment this
  deployment is not keeping** — see `docs/PRIVACY_AND_RETENTION.md`.
- **No pre-deploy command.** Migrations therefore run in the start command.
  That is safe for a single instance. Before scaling past one, move
  `alembic upgrade head` into `preDeployCommand` so concurrent boots cannot
  race on schema changes.
- **Free Postgres is temporary** and a workspace is limited to one, which is
  why the Blueprint does not provision a database by default.
- **Connection ceiling.** Render Postgres caps simultaneous connections, and
  the cap on small instances is low. `DATABASE_POOL_SIZE` plus
  `DATABASE_MAX_OVERFLOW` is the ceiling *per process*; multiply by web
  instances plus worker processes and keep the total under the cap. The
  Blueprint sets 5 + 2.

## Promoting to production

`render.yaml` deploys with `APP_ENV=staging`. That is a real decision, not an
oversight: staging validation still demands a generated `SECRET_KEY`, a
non-wildcard CORS list and a reachable Redis, but it does not yet demand RS256
keys and SMTP, so the first deploy goes green without a half-configured mail
provider blocking it.

Staging is **not** the hardened configuration. Before real families use this,
work through the list below. Each line is enforced by `_validate_environment`
in `app/core/config.py`, so the service refuses to start if one is missed —
that is the intended behaviour, and the error message names every problem at
once.

| Set | To | Why |
| --- | --- | --- |
| `APP_ENV` | `production` | Turns on the strict checks below and disables `/docs` |
| `JWT_ALGORITHM` | `RS256` | Verification keys can be distributed without sharing the signing secret |
| `JWT_PRIVATE_KEY` | PEM text | Signing key; paste as a secret env var |
| `JWT_PUBLIC_KEY` | PEM text | Verification key |
| `EMAIL_PROVIDER` | `smtp` | `console` writes verification links into the service log, and is rejected in production |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD` | your provider | Required once `EMAIL_PROVIDER=smtp` |
| `REQUIRE_EMAIL_VERIFICATION` | `true` | Otherwise anyone registers with an address they do not control |
| `TRUSTED_HOSTS` | your hostnames | Host allow-list; must not be `*` |
| `CORS_ORIGINS` | the real Admin Dashboard origin | Must not be `*`, must be non-empty |
| `FRONTEND_BASE_URL` | the real dashboard URL | Used to build links in outgoing email |
| `DEBUG` | `false` | Rejected if true |

Generate the keypair:

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out jwt_private.pem
openssl pkey -in jwt_private.pem -pubout -out jwt_public.pem
```

Paste the file contents into `JWT_PRIVATE_KEY` and `JWT_PUBLIC_KEY` as secret
environment variables. Do not commit them, and do not set `*_PATH` on Render —
its filesystem is ephemeral, and a file written at build time is not a secret
store.

### A note on `TRUSTED_HOSTS`

The Blueprint leaves it unset on purpose. Empty means the host allow-list
middleware is never installed, which guarantees Render's health check cannot be
rejected with `400 Invalid host header` on a first deploy. When you set it for
production, include the hostname Render health-checks (your
`*.onrender.com` host) alongside any custom domain, or the deploy will fail its
health check.

## Rotating leaked credentials

Two secrets were committed to this repository and pushed to
`github.com/abhinandan1588/Child-Digital-Care`, which is **public**:

| Secret | Where it was | Consequence |
| --- | --- | --- |
| Postgres password, plus internal *and* external connection URLs | `postgress details.txt`, and `app/core/config.py` as a default value | The external URL is reachable from the public internet; anyone can read and write the database |
| 3072-bit RSA JWT private key | `deploy-secrets/jwt_private.pem` | Anyone can mint valid parent, device and admin tokens — a complete authentication bypass |

Both files are now untracked and covered by the root `.gitignore`, so a future
push will not republish them. That does not undo the disclosure: **the only fix
is to replace both secrets.**

1. **Rotate the database password.** Render Postgres → your instance → the
   credential rotation control. Then update `DATABASE_URL` on the web service.
2. **Generate a new JWT keypair** (command above) and set it as env vars. Every
   existing token stops verifying, which is the point — tokens signed with the
   exposed key must stop working.
3. **Treat the data as untrusted.** The database was publicly reachable with a
   known password. Before reusing it, check for unexpected rows — or start from
   an empty instance, which is cheap while there is no production data.
4. **Scrub the history**, after rotating:

   ```bash
   pip install git-filter-repo
   git filter-repo --invert-paths \
     --path 'postgress details.txt' \
     --path deploy-secrets
   git push --force --all
   ```

   This rewrites history, so coordinate with anyone who has a clone. Rotation
   matters more than scrubbing: the values are already crawled and cached, and
   removing them from history does not un-publish them.
5. **Consider making the repository private** while this is sorted out.

Going forward, no connection string, password or key belongs in
`app/core/config.py`. Its defaults describe a local development stack only;
every deployed environment supplies its own values from Render's environment
variables.
